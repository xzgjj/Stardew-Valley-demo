# 农场生活游戏机制研究与项目参考

日期：2026-10-28。目标：给现有 Godot 工程制定可执行的农场生活 MVP，并让后续开发者知道借鉴范围、证据来源、模块接口、内容扩展顺序和素材风险。本文是分析记录，不设字数上限；它不是对《星露谷物语》的逐项复刻清单。

## 1. 研究边界与证据

本研究从公开产品说明、官方 Godot 文档、公开教程与可见开源项目页面抽取高层机制。产品页面能证明游戏公开宣传的活动类别，不足以证明内部算法、完整状态机、具体平衡参数或每一处场景细节。社区教程只代表作者实现方案，不能当成权威的原作实现，也不表示代码和素材都可复用。

《星露谷物语》官方简介列出种植与养殖、技能成长、村民日程/生日/节庆、洞穴探索、社区修复、恋爱、钓鱼、收藏、烹饪与制作等系统。[官方产品介绍](https://www.stardewvalley.net/about/) 官方游戏 Wiki 将它概述为可非线性推进的游戏，提供多类赚钱方式和活动。[新手指南](https://wiki.stardewvalley.net/Getting_Started) 这些信息说明可研究的是“玩家活动如何互相供给目标”，不能据此复制具体剧情、人物、地图、美术或台词。

Godot 4.7 已包含 2D 场景编辑与 TileMap 能力；本工程原本就是 4.7 项目，桌面安装为 4.7.2.stable，因此工程锁定该精确版本。[Godot 4.7 发布说明](https://godotengine.org/releases/4.7/) 官方 TileMap 文档建议以多个 TileMapLayer 区分图层，并支持图块绘制、重用 TileSet 和地形规则。[TileMapLayer 使用说明](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilemaps.html) 官方存档文档列出 JSON 与二进制序列化选择及类型转换边界。[存档指南](https://docs.godotengine.org/en/latest/tutorials/io/saving_games.html)

## 2. 农场生活循环拆解

### 每日层
玩家醒来后查看日期、资源与待办；在有限时间里选择整理土地、收集资源、照料作物、拜访居民或探索；一天结束时按日结算成长与其他世界状态。时间压力让“今天要做什么”成为持续的决策。MVP 只用手动结束日代替实时钟，暂不加入能量消耗、时间段、昏倒惩罚或日程模拟，防止原型同时承担经济平衡和时钟调试。

### 作物层
核心状态链为：空地 → 开垦地 → 已播种 → 已浇水 → 隔日成长 → 成熟 → 收获物 → 出售/制作/任务。工具动作必须依据目标格状态合法执行；失败时不扣物品、不修改土地。不同作物将来需要数据化的季节、成熟天数、是否可多次收获、售价和图像阶段；这些字段暂不在单一 MVP 里提前抽象。本版本用原创“日光豆”验证两次浇水—日推进—成熟—卖价的闭环。

### 经济层
收入来自采集/作物/产品等活动，支出用于种子、工具、建筑或扩展。经济的可玩性依赖节奏：初期提供目标，中期解锁更省时的选择，后期给装饰和收集空间。本轮固定初始金币、种子和作物价值，仅用于证明“劳动改变存档并回报资源”，不是原作平衡参数，也不代表成品经济设计。

### 社区层
居民以独立角色场景、独立对话资源和独立日程逐步加入。友好互动可提供情感回报和任务线索；事件应由地点、日期、关系或物品等条件触发。MVP 先用禾宁验证接近距离、按键互动、对话反馈与日期变化；姓名、衣着、背景、对白、场景位置均为本项目原创，暂不含礼物、好感、恋爱、家庭或原作事件。

### 长期目标层
公开介绍里的技能、洞穴、钓鱼、博物馆、修复项目、节日、制作、房屋定制等属于扩展系统。分析时应问每项系统补足哪类体验：

- 成长技能：让重复活动提供新选择，而非只叠数值。
- 探索区域：提供资源、风险和新地图目标，与农场收入交换时间。
- 制作/烹饪：把低阶资源转为专用用途和品质更高的产物。
- 居民/任务：把物品、地点、日期和人际关系连成情境目标。
- 节庆/收藏：在每日重复循环里加入低频变化和完成度目标。

本轮不实现这些项目；只有在作物循环、保存、工具反馈稳定后逐项评估。非线性自由也不等于无目标：原型至少应同时给一条短期收获目标、一条社交反馈和一条未来解锁线索。

## 3. 系统和接口建议

| 系统 | 当前职责 | MVP 边界 | 后续扩展接口 |
|---|---|---|---|
| GameState | 日期、金币、种子、地块、收获数、存档 | 单实例、JSON 用户存档 | 存档版本迁移、世界状态分片 |
| Farm Plot | 开垦/播种/浇水/成长/收获规则 | 地块坐标字符串键，单一种子 | CropDefinition 资源、土壤/天气修饰 |
| Player | WASD 移动、朝向、面前格 | 直线平面，无地图阻挡 | 工具动画、碰撞、体力、手柄 |
| Interaction | 识别距离并给出动作反馈 | 仅禾宁对话 | 交互目标协议、物件/告示牌/门 |
| HUD | 日期和资源，显示提示 | 单面板 | 背包、快捷栏、地图、对话框 |
| World | 地表、路径、田地、房子 | 40×22 固定图 | 多场景、门、室内、天气、遮挡排序 |
| Asset pipeline | 当前 SVG 占位素材 | 原创、无第三方依赖 | Aseprite 源文件、许可证清单、导出规则 |

状态变更由 GameState 的方法执行，视图只读状态并重绘 TileMapLayer。场景负责输入路由、最近交互对象和提示文本，不复制日期、金币或作物成长规则。这个边界足以支持当前原型，不应在没有第二个真实用例前创建通用事件总线、复杂 ECS、脚本化任务语言或自研引擎。

## 4. 场景树基线

当前主场景 `scenes/main.tscn` 只组合六类节点：Ground、Soil、Crops、Decorations、Player、Villager、HUD。三层 TileMapLayer 表达地表、土壤、作物；人物独立为可复用场景；村民的初始互动文本由角色脚本返回；全局 GameState 由 Autoload 保持日期与存档状态。后续地图扩大时可以拆成 `FarmOutdoor`、`HouseInterior` 等独立场景，切换入口仍沿用一个场景切换边界。禁止把全部地图、NPC、UI、道具和存档都写进 `main.gd`。

第一阶段的空间关系：玩家出生在农田左侧，3×3 可操作格位于地图中央偏左，原创小屋与村民在右侧，路径连接画面区域。地块可以覆盖或擦除图层，物理阻挡暂缺；最终表现需要真实像素素材后再做视觉审查。这个布局是项目自己的原型地图，不以任何原作地图坐标或外观为参照。

## 5. 当前 MVP 的行为契约

1. 开垦只对不存在的地块成功；重复开垦不得改变已有作物状态。
2. 播种要求地块存在、没有作物且种子库存大于零；成功消耗一颗种子。
3. 浇水要求已播种且当天未浇水；重复浇水不应产生状态变化。
4. 只有已浇水作物在日推进后增长；未浇水时不增长。一天最多长一阶段。
5. 未成熟作物不能收获；成熟收获清除作物、保留土壤、金币增加 20、收获数加一。
6. `to_data`/`load_data` 保留日期、库存、金币、收获数和地块数据；坏数据不能把日期变为 0 或让库存为负。
7. 每个合法/不合法动作都可在 HUD 上看出结果。场景和状态逻辑保持一致。

这些契约通过 `tests/test_game_state.gd` 的最小状态测试保护。状态规则用单元边界测试；后续实际输入、UI、存档文件工作流再增加一个端到端 smoke，不在每一层重复检查同一个行为。

## 10. 系统依赖与功能优先级

下表的“原作事实”仅限官方简介公开列出的内容；“设计推导”是对如何形成体验的解释，需要通过原型验证，不应写成原作源代码事实。

| 系统 | 对玩家的价值 | 主要依赖 | 先后顺序与判断 |
|---|---|---|---|
| 日历与时间 | 决定今日行动机会和季节计划 | 游戏时钟、睡眠、存档 | 首先验证手动日推进，稳定后才做实时分钟和行动耗时 |
| 农地与作物 | 提供可计划、可见、可回报的核心劳动 | TileMap、地块状态、作物定义、成长结算 | 当前已实现一个简化闭环，下一步先验证输入和 UI 易用性 |
| 资源与金币 | 让行动结果积累成购买或解锁能力 | 物品定义、存档、出售/购买入口 | 当前只验证状态余额变化，后续再做价格曲线 |
| 工具与移动 | 将玩家意图映射到周边世界格子 | 输入、朝向、交互距离、地图碰撞 | 当前按面前格执行，无工具动画、体力、工具升级 |
| 社区角色 | 给玩家提供社会反馈、地点信息和长期关系 | 对话、日期、角色状态、地点 | 当前只有原创村民一句轮换问候，不做关系数值 |
| 探索活动 | 产生不同节奏的风险、收集和新资源 | 区域切换、遭遇、战斗/钓鱼规则 | 首轮不能同时开发；需先确认核心玩家喜欢哪种扩展 |
| 制作与烹饪 | 消耗已有资源，换取新用途和效率 | 配方数据、工作台、物品背包 | 依赖物品模型稳定后再上，不为一条配方造规则引擎 |
| 任务与修复目标 | 把资源和居民互动连接成阶段目标 | 任务状态、物品交付、事件/存档 | 先做单条原创任务验证反馈，再决定是否需要通用任务框架 |
| 节庆与季节 | 为循环活动加入周期变化 | 日期、地图变体、NPC 日程、对话 | 依赖日历与事件系统，不能先做一堆节日场景 |
| 房屋与农场布置 | 允许玩家表达偏好和改造空间 | 可放置物、网格、碰撞和存档 | 当前暂缺；需要先解决家具落点与场景序列化 |

优先级的推导原则是：如果一项功能没有依赖已稳定的状态，不要以完整系统的形式实现。比如先完成地块保存和作物阶段，再加多个季节；先实现单个交互人物，再加每日行程；先确认单一物品可被种植、消耗和出售，再做完整背包 UI。这样每个里程碑都能以可观察行为验收。

## 11. 地块状态图与存档约束

MVP 的地块不是 TileMap 上一个颜色，而是可持久化的逻辑对象。地表绘制负责呈现状态；GameState 负责确定动作是否成立。状态变化表：

```text
不存在地块 --开垦--> 已开垦空地 --播种--> 未浇水作物
未浇水作物 --浇水--> 当日已浇水作物 --结束当天--> 已成长/次日未浇水
已成长作物 --再次浇水与结束当天--> 成熟作物 --收获--> 已开垦空地
```

规则边界需要处理重复输入：对空地浇水失败；对作物重复浇水失败；没有种子时播种失败；未成熟时收获失败；结束当天时已浇水标记清除；未浇水作物不能增长。失败动作不应改变种子、金币、成熟度或收获计数。地图层与状态不一致是首轮发现的一个重要风险：如果田地视觉上是耕地，逻辑状态也必须预建为耕地；否则玩家需要理解看不见的前置条件。

存档数据采用“能重建游戏状态的最小数据”原则。当前存日期、金币、种子、收获数、地块坐标和地块字段。不存 TileMap 的最终像素颜色，因为显示可由逻辑数据重建。未来加入存档版本字段后，新版读旧档要有迁移测试；损坏/缺字段存档要安全失败，并给出日志，不能静默把玩家进度覆盖为默认状态。当前序列化只做 MVP 行为验证，还没有版本迁移或文件损坏恢复。

存档完整性验收应包含：新档从默认值启动；推进一天后日期增加；有水作物进入成长阶段；读档恢复同一作物和库存；读不存在的档不崩溃；加载损坏文本不覆盖现有内存状态。最后两项尚未实现，列入稳定性任务，不宣称当前已有完整防损坏能力。

## 12. 操作与 UI 的审查清单

原作的输入设备、逐格工具瞄准、指针行为和全部 UI 细节不在本轮复刻。我们的 MVP 使用键盘热键，只用于快速检查农场循环。后续正式工具栏要回答以下问题：当前选中工具是什么、目标格为什么合法或不合法、操作是否消耗资源、动作冷却期间会发生什么、是否支持取消、手柄/键鼠如何共享一套语义。提示不应只用颜色区分地块状态；应有文字、形状或图标差异，确保色觉不敏感玩家仍可辨别。

当前主场景的文字位置和比例是临时排版，无法作为最终可读性结论。实际运行中的截图审查需关注：全屏缩放时字体是否太小；地块 16×16 图块与角色身高比例是否清楚；HUD 是否遮挡角色/重要位置；对话信息是否能读完；提示在使用中文字体下是否缺字；帧缩放是否保持像素边缘清晰。Godot 使用 SVG 导入，最终像素图仍须检查采样过滤和缩放设置。

后续图层顺序建议为：底地、路径/水面、地块土壤、作物、低矮对象、人物、树木前景/屋檐、UI。树、屋檐或高植被需要按人物脚底 Y 坐标进行遮挡排序，不能仅依赖全场景固定 z_index。当前原型只有小屋占位绘制，没有树木遮挡或动态排序，不把这点当成功能。

## 13. 研发风险及缓解方法

### 内容规模失控
风险：用户希望覆盖原作完整功能，但“农场、居民、道具、剧情、地图、节庆”可无限增加，轻易超过单人 MVP。缓解：先锁定一个场景、一个主角、一个村民、单一种子和一条收益闭环；其他功能作为已记录的后续里程碑，不在第一场景塞假接口。

### 知识产权与授权
风险：模仿素材可能演变成直接描摹原作图像，或网络素材只有个人用途授权。缓解：美术需求按像素尺寸、色板、动画帧和可读性描述；角色设定、轮廓、配色组合、对白、地图布局从项目自己的背景故事出发。每包素材写明许可和来源；出现不明授权就不导入。此策略是项目治理约束，不是对任何个案授权范围的法律结论。

### 用户指定远端无法访问
事实：本地 `git ls-remote` 因 DNS/网络初始化失败；Web 读取也未取得仓库页面，因此当前没有默认分支、LICENSE 或提交历史证据。缓解：远端恢复访问后只读检查分支和文件树，先保存当前头引用/归档；确认许可后在本地自己的工作分支上集成，最后才评估是否更新指定仓库。不要把未经审查的远端克隆直接覆盖本地工程。

### 工程边界与既有插件
风险：原工程带有 Tripo3D bridge 插件，可能与 2D 玩法无关，贸然移除会破坏已有用户工作流。缓解：保持插件文件和启用状态不动；后续如启动/导出时产生实际冲突，再提供具体验证差异，由人决定是否禁用。

### 保存与规则脱节
风险：每新增字段后只修改内存逻辑，存档没有写入，重启后出现丢失或状态损坏。缓解：每个持久化系统新增时同时更新 to_data/load_data、迁移策略和回归检查。测试关注外部能观察到的恢复结果，不盲目复制整个存档实现作为预期。

### CI 仅在本地存在
风险：Workflow 文件本身不能阻止管理员绕过保护，缺少远端规则设置时可能有人直接推送或关闭检查。缓解：将 `CI`、`scope`、`policy-approval` 作为必须状态检查；目标仓库启用 PR 必需审核、禁止强推、CODEOWNERS 与当前头审批；记录规则配置时间及基线版本。远端权限未核验，目前不能声明这些托管设置已生效。

## 14. 假设、验证计划和决策点

以下内容是当前推导，而非调研事实：

1. **键盘 MVP 可验证种地循环。**验证：试玩者不读源码，也能依据 HUD 完成至少一轮播种到收获；如需反复解释，优先改 UI 而非加规则。
2. **一个村民足以检查场景抽象。**验证：新增第二个原创村民只需场景资源和数据，不复制整个交互系统；如果做不到，再抽取共性。
3. **数据 TileMap 层适合这个规模。**验证：扩大到一个小镇后，地图编辑、碰撞、排序仍能在 Godot 编辑器中可见维护；若动态铺格成为痛点，再评估 LDtk/Tiled 导入。
4. **JSON 适合早期人可读存档。**验证：加入季节与 NPC 状态后文件仍便于调试；若频繁类型转换或数据量增长，再对比二进制序列化，迁移必须兼容旧档。
5. **Godot GDScript 降低迭代成本。**验证：场景/脚本错误可由编辑器和 CI 捕获，日常开发不需要先维护自研引擎；性能问题实测后才考虑 GDExtension。
6. **单个中心场景可支撑第一小段体验。**验证：主场景节点数量和脚本职责仍清楚；加入第二张地图、室内或菜单前就拆分职责，不为未来可能性先造通用场景管理框架。

游戏发行前需通过真实试玩采集：用户在单日中最喜欢哪类活动；对动作提示是否理解；作物成长时长是否有等待感；社交反馈是否足够；地图大小是否适合屏幕。没有试玩数据时，把价格、周期、内容数量当作临时占位，禁止以“和原作完全一样”作为平衡目标。

## 15. 设计参照，不直接照抄

在可获得正版游戏的前提下，观察者可以从体验层面记录：一天里玩家因何改变计划；作物等待期间是否有其他可做活动；商店或任务如何形成短期目标；NPC 互动是否能在玩家主动探索时被发现；失败或错过某项活动后是否还有替代路径。记录玩家感受和系统因果即可，不记录可复画的地图切片、对白逐字稿、人物肖像尺寸或可直接复制的物品图。

建议为每次竞品观察填写以下模板：

| 观察字段 | 示例提问 |
|---|---|
| 目标 | 玩家此刻想完成什么？ |
| 约束 | 哪个资源、时间或空间限制了选择？ |
| 反馈 | 行为后立即得到什么视觉/音频/状态反馈？ |
| 延迟回报 | 结果何时返回，玩家如何知道还要等多久？ |
| 替代活动 | 当一个动作暂时不能做时，世界提供什么选择？ |
| 本项目改写 | 我们能否用原创角色、资源与场景表达同一类玩家价值？ |
| 验证方式 | 试玩者完成行为的时间、失败原因和自述是什么？ |

借鉴的目的是理解“玩家为什么做”，不是复制“作品怎么画、怎么说”。如果一个设计点只有照着特定原作角色或剧情才成立，就不属于当前可以复用的高层系统。

## 16. CI 规则与本文档的对应关系

| 已记录风险 | 自动检查 | 需要人工负责的判断 |
|---|---|---|
| 规划文档越写越长 | 核心文档 3000 字符预算 | 内容是否值得保留、研究记录是否有证据 |
| 复制粘贴重复段落/代码 | 段落检查及 8 行重复逻辑扫描 | 抽象是否必要，重复是否合理 |
| 小任务变大重构 | 路径白名单、50 文件/2400 行预算 | 是否批准扩大本任务范围 |
| 代码过长或难分析 | 单文件 300 行、圈复杂度 10、Lint/格式 | 命名、节点职责和具体设计是否易读 |
| 通过删测试让 CI 变绿 | 保护断言清单、测试删除门禁 | 行为变化是否合理、用例是否可替换 |
| 顺手关闭 CI 或改宽阈值 | 指定账号当前头审批和 CODEOWNERS | 批准者与开发者身份是否真正分离 |
| 只改源码而忘记文档 | 文档版本一致性与预算 | 规格对玩家价值描述是否准确 |
| CI 跑到时间失控 | Workflow 10 分钟限制，无自动无限重试 | 第三次仍失败后是否拆解工作 |

自动扫描对静态文本可判定的边界是有限的：没有引用的脚本可查，但反射调用或场景路径拼接可能漏掉；重复 8 行以上代码可查，但同一逻辑被改名重写不一定发现；圈复杂度不能代替代码设计评审。CI 的结果是筛查证据，不能自动替代人工判断。

## 17. 后续完整游戏的阶段验收建议

- **Farm Slice**：一块可耕地、多个作物、日推进、睡眠与存档；从启动到收获的一条完整路径可重复运行。
- **Town Slice**：至少两张地图、原创居民、对话和任务交付；地图出口和居民日程数据与场景逻辑分开。
- **Economy Slice**：种子购买、产品出售、升级目标；用表格模拟早/中期收益，不靠代码散落常量调价。
- **Season Slice**：至少两个季节、作物可种期、季节交替清理和天气；旧存档迁移、错过时机的补偿路径均有定义。
- **Exploration Slice**：先选钓鱼、采矿或采集其中一个，做完整活动闭环再增加第二个；定义输入、风险、奖励和退出方式。
- **Social Slice**：原创角色档案、固定日程、礼物偏好、事件触发和关系影响；不复制原作的生日表、事件台词或角色关系网。
- **Release Slice**：输入重映射、字幕/文本可读性、存档备份、平台导出、崩溃恢复和授权清单齐全；发布包不包含未授权素材或调试文件。

阶段验收由用户故事和边界案例组成，不按“实现了多少与原作相同的菜单”计量。每个系统最少回答：什么玩家问题由它解决；它依赖什么；什么状态保存在档案里；失败时会发生什么；它如何被人试玩；哪项可自动验证，哪项必须人工评审。
